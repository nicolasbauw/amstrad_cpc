- WEC Le Mans (2è bug, OUVERT, piste : pointeur de flux 0x08C6) : redémarrage ~1,18 s après le lancement de la course. MÉCANISME ENTIÈREMENT ÉLUCIDÉ : le jeu dispatche sur un type d'objet 15 dont l'entrée de table (0x43DC+15*4) pointe vers 0xEF06 ; les DEUX ROM sont désactivées, donc 0xEF06 est de la RAM contenant FF FF FF FF FF FF FF EE 00 00... -> 7 RST 38, un XOR, puis une glissade de NOP jusqu'à ce que PC déborde de 0xFFFF à 0x0000 = reset. ~0,2 s, ce qui recolle avec les mesures. (Correction : PAS de corruption de SP, contrairement à une note antérieure — les 21 bascules de la pile de secours 0x309F/0x310D sont toutes équilibrées.) COMPARAISON EXHAUSTIVE AVEC CAPRICE32 (64 Ko de RAM brute, même état logique) : seulement 78 octets/65536 diffèrent, tous de l'état d'exécution (pile 0x021A-0x023A, variables 0x31xx-0x39xx). Les 4 zones critiques sont IDENTIQUES octet pour octet : données de dispatch 0x4360-0x438F, table 0x43DC, table d'objets 0x8600-0x87FF, et le contenu de 0xEF06. RAM initialisée à zéro des deux côtés. (L'écart supposé sur 0x4375 — 0x50 chez nous vs 0x1F — était un ARTEFACT : on comparait notre vue bankée du CPU à leur RAM brute. En RAM brute, 0x1F des deux côtés.) VRAI CODE TROUVÉ (le désassemblage linéaire autour de 0x2652 était faux, PC n'y passe jamais) : c'est un décodeur de flux en 0x2642-0x2661, type = (octet_de_flux - 0x10) & 0x0F, avec le pointeur de flux en RAM à 0x08C6 (et des compteurs en 0x08C5/0x08BC/0x08BF). L'octet lu est 0x1F -> type 15. POINTEUR DE FLUX VÉRIFIÉ ET CORRECT (hypothèse du décalage d'un octet écartée) : l'init suit un schéma régulier pour 4 flux (pointeur=base, compteur=premier octet) en 0x04CC-0x04ED ; le 0x10 en 0x4374 est le compteur initial, 0x1F en 0x4375 est bien le 1er octet de flux. L'encodage est du RLE (octet 0xNM = N objets de type M), donc 0x1F demande légitimement un objet de type 15. La base 0x4374 est une constante immédiate dans du code identique à Caprice32. => CONCLUSION RETOURNÉE : avec la même RAM et un décodeur déterministe, Caprice32 saute FORCÉMENT lui aussi vers 0xEF06. La divergence est APRÈS le saut, pas dans le calcul de l'index. (Écarté aussi : le repli sur ROM 0 pour un numéro de ROM haute inexistant — on avait relevé selected_high_rom=255 — est déjà correct chez nous, cf. Memory::effective_high_rom.) PREUVE DIRECTE DU MÉCANISME : le dispatcher empile 0x1F04 comme adresse de retour avant son JP (HL), donc la routine de type 15 est censée finir par RET. En réécrivant 0xEF06 avec 0xC9 (RET) à chaque pas, LA COURSE SE DÉROULE PARFAITEMENT (écran complet, voiture, chrono, score, aucun reboot). Mécanisme confirmé de bout en bout. ÉCARTÉ : aucun code n'est censé être chargé en 0xEF06 — zéro écriture dans 0xEF00-0xEF3F entre le lancement de la course et le reboot ; la zone garde des données graphiques. DEUX ARTEFACTS DE MESURE CORRIGÉS : (a) le banking n'explique rien — au menu ram_config=0 et vue bankée = RAM brute = 0x1F, donc la comparaison des 64 Ko était valide ; (b) l'écart "0x50 puis 0x1F à t=12,777s" était ENCORE une base de temps différente (3e fois sur cette enquête — règle : comparer à ÉTAT DE JEU identique, jamais à temps écoulé identique). BILAN : tout ce qui est mesurable de notre côté concorde et ne montre aucune anomalie (données identiques, pointeur/compteur de flux corrects, RLE légitime, repli ROM correct, RAM zérotée, aucun chargement en 0xEF06). Avec les mêmes données et le même code, Caprice32 devrait sauter lui aussi vers 0xEF06 — or il ne plante pas. ÉCARTÉ : LE PLANTAGE NE DÉPEND PAS DE LA ROM. Rejoué chez nous avec la ROM ANGLAISE de Caprice32 (rom/cpc6128.rom, 32 Ko combinée) : menu correct, et reboot à t=1,1907s — exactement comme en AZERTY (1,18s). C'est bien notre émulation. (Détail utile : la position matricielle d'une touche est MATÉRIELLE, pas liée à la ROM — "2" = ligne 8 bit 1 sur tout CPC. Mais notre table autotype::key_for_char est calée AZERTY : pour piloter une ROM anglaise il faut permuter A/Q et W/Z — W est en (7,3) et non (8,7) qui est Z, et le guillemet est SHIFT+(8,1).) BLOCAGE "TOUCHE 2" SOUS CAPRICE32 : DIAGNOSTIQUÉ, ce n'est PAS un problème d'injection. En journalisant les lignes de matrice interrogées au menu, le jeu scrute bien les 10 lignes ET matrix[8]=FD (bit 1 à zéro) : la touche est donc effectivement injectée et effectivement lue — le jeu la voit et l'ignore. Les 5 échecs précédents étaient donc mal diagnostiqués (harnais accusé à tort). Le relevé "0 dispatch vers 0xEF06" obtenu au passage est sans valeur, le jeu n'étant jamais entré en course. Reste à chercher ce que le menu attend d'autre (état interne, fin de chargement disque, lecture manette...), ou à contourner. PROCHAINE ÉTAPE : finir ce diagnostic clavier ; si la ligne 8 n'est jamais lue, le jeu attend autre chose de ce côté. Sinon, contourner définitivement le clavier via un export .sna depuis notre émulateur (format simple, Caprice32 sait le charger) — ce qui bisecterait proprement et constitue une fonctionnalité utile en soi.
