- WEC Le Mans (2è bug, OUVERT, piste : pointeur de flux 0x08C6) : redémarrage ~1,18 s après le lancement de la course. MÉCANISME ENTIÈREMENT ÉLUCIDÉ : le jeu dispatche sur un type d'objet 15 dont l'entrée de table (0x43DC+15*4) pointe vers 0xEF06 ; les DEUX ROM sont désactivées, donc 0xEF06 est de la RAM contenant FF FF FF FF FF FF FF EE 00 00... -> 7 RST 38, un XOR, puis une glissade de NOP jusqu'à ce que PC déborde de 0xFFFF à 0x0000 = reset. ~0,2 s, ce qui recolle avec les mesures. (Correction : PAS de corruption de SP, contrairement à une note antérieure — les 21 bascules de la pile de secours 0x309F/0x310D sont toutes équilibrées.) COMPARAISON EXHAUSTIVE AVEC CAPRICE32 (64 Ko de RAM brute, même état logique) : seulement 78 octets/65536 diffèrent, tous de l'état d'exécution (pile 0x021A-0x023A, variables 0x31xx-0x39xx). Les 4 zones critiques sont IDENTIQUES octet pour octet : données de dispatch 0x4360-0x438F, table 0x43DC, table d'objets 0x8600-0x87FF, et le contenu de 0xEF06. RAM initialisée à zéro des deux côtés. (L'écart supposé sur 0x4375 — 0x50 chez nous vs 0x1F — était un ARTEFACT : on comparait notre vue bankée du CPU à leur RAM brute. En RAM brute, 0x1F des deux côtés.) VRAI CODE TROUVÉ (le désassemblage linéaire autour de 0x2652 était faux, PC n'y passe jamais) : c'est un décodeur de flux en 0x2642-0x2661, type = (octet_de_flux - 0x10) & 0x0F, avec le pointeur de flux en RAM à 0x08C6 (et des compteurs en 0x08C5/0x08BC/0x08BF). L'octet lu est 0x1F -> type 15. POINTEUR DE FLUX VÉRIFIÉ ET CORRECT (hypothèse du décalage d'un octet écartée) : l'init suit un schéma régulier pour 4 flux (pointeur=base, compteur=premier octet) en 0x04CC-0x04ED ; le 0x10 en 0x4374 est le compteur initial, 0x1F en 0x4375 est bien le 1er octet de flux. L'encodage est du RLE (octet 0xNM = N objets de type M), donc 0x1F demande légitimement un objet de type 15. La base 0x4374 est une constante immédiate dans du code identique à Caprice32. => CONCLUSION RETOURNÉE : avec la même RAM et un décodeur déterministe, Caprice32 saute FORCÉMENT lui aussi vers 0xEF06. La divergence est APRÈS le saut, pas dans le calcul de l'index. (Écarté aussi : le repli sur ROM 0 pour un numéro de ROM haute inexistant — on avait relevé selected_high_rom=255 — est déjà correct chez nous, cf. Memory::effective_high_rom.) PROCHAINE ÉTAPE : la seule chose qui puisse différer sans apparaître dans un diff de RAM, c'est l'ÉTAT DE COMMUTATION MÉMOIRE. Chez nous au moment du saut : ROM basse ET ROM haute désactivées -> 0xEF06 = RAM -> glissade de NOP -> reset. Si Caprice32 a la ROM haute ACTIVÉE à cet instant, 0xEF06 y est du code ROM réel et le saut n'a rien de fatal. À relever des deux côtés au moment exact du JP (HL) : rom_low_enabled / rom_high_enabled / numéro de ROM sélectionné, et ce que le CPU lit vraiment en 0xEF06 à cet instant (et non au menu, seul point comparé jusqu'ici). Voir doc/wec-le-mans-race-crash.md.
