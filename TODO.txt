- Bruce Lee : après le lancement de la partie (deux ENTRÉE), seule une fraction du décor s'affiche. Cause identifiée : la table d'encres du firmware (0xB7D5-0xB7E5) ne reçoit que 4 couleurs sur 16, le reste reste gris (indiscernable du fond). Mécanisme d'écriture localisé (fonction ROM générique 0x0CFD-0x0D19), mais pas encore l'appelant qui s'arrête prématurément à l'index 3. Voir doc/bruce-lee-palette.md pour la suite. Même remarque que BMX Simulator ci-dessus : à retester avec le correctif RST/interruption.
- WEC Le Mans (2è bug, OUVERT, piste : pointeur de flux 0x08C6) : redémarrage ~1,18 s après le lancement de la course. MÉCANISME ENTIÈREMENT ÉLUCIDÉ : le jeu dispatche sur un type d'objet 15 dont l'entrée de table (0x43DC+15*4) pointe vers 0xEF06 ; les DEUX ROM sont désactivées, donc 0xEF06 est de la RAM contenant FF FF FF FF FF FF FF EE 00 00... -> 7 RST 38, un XOR, puis une glissade de NOP jusqu'à ce que PC déborde de 0xFFFF à 0x0000 = reset. ~0,2 s, ce qui recolle avec les mesures. (Correction : PAS de corruption de SP, contrairement à une note antérieure — les 21 bascules de la pile de secours 0x309F/0x310D sont toutes équilibrées.) COMPARAISON EXHAUSTIVE AVEC CAPRICE32 (64 Ko de RAM brute, même état logique) : seulement 78 octets/65536 diffèrent, tous de l'état d'exécution (pile 0x021A-0x023A, variables 0x31xx-0x39xx). Les 4 zones critiques sont IDENTIQUES octet pour octet : données de dispatch 0x4360-0x438F, table 0x43DC, table d'objets 0x8600-0x87FF, et le contenu de 0xEF06. RAM initialisée à zéro des deux côtés. (L'écart supposé sur 0x4375 — 0x50 chez nous vs 0x1F — était un ARTEFACT : on comparait notre vue bankée du CPU à leur RAM brute. En RAM brute, 0x1F des deux côtés.) VRAI CODE TROUVÉ (le désassemblage linéaire autour de 0x2652 était faux, PC n'y passe jamais) : c'est un décodeur de flux en 0x2642-0x2661, type = (octet_de_flux - 0x10) & 0x0F, avec le pointeur de flux en RAM à 0x08C6 (et des compteurs en 0x08C5/0x08BC/0x08BF). L'octet lu est 0x1F -> type 15. PROCHAINE ÉTAPE : remonter à l'initialisation du pointeur 0x08C6 au lancement de la course. Un décalage d'UN SEUL octet expliquerait tout : 0x4374 vaut 0x10 (-> type 0, inoffensif) et 0x4375 vaut 0x1F (-> type 15, fatal). Si le pointeur est correct, alors Caprice32 dispatche aussi vers 0xEF06 et la divergence est APRÈS le saut. Voir doc/wec-le-mans-race-crash.md.
