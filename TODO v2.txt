Ma vision : je souhaite un émulateur qui puisse à la fois satisfaire ceux qui souhaitent simplement jouer, mais aussi les power users. Donc : capable de se lancer simplement du desktop et charger des jeux avec une interface simple. ET aussi de continuer à proposer les fonctions avancées actuellement disponibles via la console (en se désolidarisant du terminal de lancement de l'émulateur) et de proposer aussi l'écran "machine status". Et de proposer aussi un shader CRT : ça devient commun, presque une norme dans les émulateurs. Je souhaite que ByteBox se distingue des autres en réunissant tous ces points. C'est presque plus qu'un todo, ça devient un document d'architecture UX qui va dicter des choix techniques.

- pour être davantage "professionnel", j'aimerais étudier la possibilité de passer par QT pour l'interface graphique : meilleure intégration à l'OS, distinction avec les autres émulateurs... Plusieurs questions à se poser:
1) peut-on toujours utiliser SDL pour gérer nos inputs (clavier, manette) ?
2) peut-on intégrer un rendu vulkan dans une fenêtre QT ? (voir plus bas, la question du shader)

- quand l'émulateur est lancé via le raccourci desktop, il se lance donc sans terminal, et donc sans commandes à lancer depuis notre "console" - et donc, comment se passe le spawn du thread console, et l'écoute des évènements ? C'est problématique et j'ai remarqué que dans ce cas, le CPU du host s'emballe. L'idée est donc :
1) On va créer notre propre fenêtre de commandes, via par exemple lighostty (https://github.com/Uzaaft/libghostty-rs), ou avec un système de notre cru, affichable par la touche F11 (pour être cohérent avec la fenêtre de state via F12), qui remplacerait le terminal d'ou est lancé l'émulateur, car c'est une adhérence dont je souhaite me débarasser.
2) il nous faut aussi (via la touche de fonction F6) une fenêtre SDL (ou QT) séparée (comme l'est celle du "machine status"), qui permet d'insérer des disquettes/cassettes, et paramétrer de façon visuelle ce qui est actuellement disponible dans le fichier de conf. Reprendre le code esthétique de la fenêtre de paramétrage de winuae/amiberry. Question subsidiaire : SDL (ou QT) permet-il d'ouvrir une fenêtre de sélection de fichier qui est agnostique et/ou intégré au système (gnome, kde, windows, mac, etc...) ?

- j'aimerais adapter le code pour avoir la possibilité d'un shader CRT en utilisant vulkan. Le shader doit pouvoir s'adapter aux différentes résolutions (X1; X2, X3, fullscreen) pour avoir un rendu identique. Les scanlines ne doivent pas être trop prononcées ! elles doivent être visibles mais réalistes (le rendu CRT n'était pas si mal après tout). Les pixels doivent avoir un rendu plus rond, comme à l'époque sur un CRT. Le shader CRT doit être activable/désactivable via la touche F5.

- implémenter un clavier virtuel dans une fenêtre SDL/QT (affiché/masqué via la touche F7), qui reprend de façon stylisée l'esthétique d'un clavier de 6128 azerty (dont je peux fournir une photo de référence) : je ne veux pas tomber dans le délire des keymaps (j'avais connu un enfer en adaptant mon émulateur TRS-80 pour SDL3). Pour la plupart des cas d'usage, cela suffira, et le paramétrage actuele est 100% parfait pour mon clavier Mac sous Linux, je ne souhaite pas changer cela.
